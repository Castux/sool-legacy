===========================================

The sool programming language specification

Introduction

This document is the specification for the sool programming language. It consists in a formal definition of the language's core mechanics, grammatical rules, along with the semantics they represent, and a complete description of the built-in classes and standard libraries.

It is meant as a normative reference for the implementation of a translator and runtime, and as such is a useful and necessary ressource for the programmer who uses the language. Therefore, as in any specification, the terms "must", "should" and "may" take their usual meanings from the English language: "must" indicates a definitive requirement, "should" specifies recommended features of a good implementation, and "may" is simply an option that can be safely ignored without compromising the compliance to the language or performance. Anything not explicitely qualified by one of these words is to be considered a "must".

Even though this document will give examples to illustrate the definitions, it is definitely not a tutorial and might not be the easiest way to get acquainted with the language. It is nevertheless recommended to read it through at least once, if only to know where to look for information when needed.

Notation

Grammar production rules are written in the usual Extended Backus-Naur Form. A monospace font is used for code examples, standard identifiers and grammar rules. An italic font is used when new terms are defined.

Disclaimer

sool is a work in progress. It is an experiment, and as such its design is constantly evolving. Any information in this document might change later, and the global state of the language is to be considered temporary.

Only when the language specification will be frozen shall this disclaimer be removed, and a version number given to the language.

Basic concepts

sool is a general purpose, imperative, class-based, statically typed, memory safe and garbage collected language. It aims at combining the ease of dynamic interpreted languages with the performance of compiled languages. It is a delicate compromise between expressivity, simplicity and execution speed.

Its grammar is simple, and avoids redundancy as much as possible when the programmer's intention is clear. It is obvious and unsurprising. An experienced programmer should be able to fluently read and understand sool code without prior knowledge of the language, and learn to write it very fast.

sool is not particularly innovative. It only tries to combine existing concepts in a coherent and harmonious language, pleasant to use and easy to maintain.

Objects and values classes

sool is centered around the concept of class. Every element of data manipulated in sool is an instance of either a value class or an object class, called respectively a value or an object. While the class is a model that defines data components and behaviors, an instance is a specific application of this model to data.

Variables are used to store and manipulate values and objects. sool is strongly typed, which means that a given variable can only hold instances of a single class. Along with additional information, this constitutes the type of the variable. Type is checked at compile time. In practice, it means that every variable is either declared with a class information, or the class information is inferred from the code by the compiler.

The essential difference between values and objects are how they are stored in variables and manipulated. Values, as their name suggest, are manipulated "by value". The data is actually contained in the variable, and copied at assignment or when passed as argument to a method. On the other hand, objects are manipulated "by reference". When an object is created, its data is stored in dynamically allocated memory, and the variable recieves only a reference to it. Likewise, an assignment results only in copying the reference. The manipulated object is the same.

Built-in classes

sool provides primitive classes, that cannot be broken down to smaller components.

Value class num is the general purpose number. It is implemented as the IEEE 754 double-precision binary floating-point format. It can contain integers in the range +/- 2^53 with no loss of precision, and real numbers roughly in the range +/- 1.7e308 wity varying accuracy.

Value class uint is the unsigned integer. Its size is at least equal to the size of an address on the target machine. It is used mostly for indices in loops and arrays, and to hold opaque pointers from foreign code.

Value class bool is the classic boolean. It can hold exactly two values: false and true, and is the base of binary logic and program flow control.

Value class text represents sequences of Unicode codepoints. They should be implemented as references to internized immutable arrays of 32 bits unsigned integers, which makes them semantically equivalent to values, but with increased efficiency in particular for comparison.

Although sool is meant as a very high-level language, it provides the data object class to make binary manipulation possible. data represents a sequence of bytes to and from which can be written and read arbitrary binary information, convertible to and from other sool classes.

The only built-in complex class in sool is the array, which acts as an homogenous sequence of variables. It is a dynamic object that can be grown or shrunk and manipulated through slices: multiple references to the same data.

Every other class - whether it is user provided or from the standard library - is a composite class, built with sool code by combining other classes and defining behaviors.

Methods and messages

All data in sool is manipulated as instance of a class. A class defines members, that is objects and values it contains, and methods, procedures that manipulate the data, perform calculations or have side-effects.

There are no "functions" in sool. Every procedure or algorithm is a method attached to a class. Just like all data is an instance of a class, (almost) every operation is the execution of a method, including reading and writing to an object's member, indexing an array, and applying a binary operator.

This is a core concept of sool. Members and methods are accessed using the same syntax, and more importantly, members and methods can be used interchangeably: accessing a member is simply executing a method that returns its value. Similarly, calling a method that returns a single value can very well be a simple member access. In particular, members and methods participate equally to the interface mechanism.

Asking an instance to execute a certain method is called sending a message to this instance. Although fundamentally procedural in nature, a sool program can be seen as a group of class instances being spawned into existence and sending messages to each other.

Generic programming

sool supports two forms of generic programing: class templates and generic classes.

Templates are classes in which one or more types are left unspecified. The class template is then specialized by explicitly providing class names to be used as template arguments. This is done at compile time, and the resulting specializations are strictly equivalent to having duplicated the class's code for each set of arguments. The built-in array class is an example of template.

Generic classes are sool's mechanism for polymorphism. Any class that complies with a given interface, ie. implements a given set of methods, can be casted to the corresponding generic class. These generics work otherwise like any other class: methods can be written for them, variables can use them as types, they can be passed as method arguments and return values. An algorithm can be written once and applied to any class that has a compatible interface.

While generic classes often allow more concise and elegant code than templates, they are naturally slower due to their internal workings: they use dynamic dispatch to allow the same machine code to work with any class instance.

Garbage collection and memory safety

sool is fully garbage collected. Every object is allocated dynamically in memory, and its existance is guarantied as long as there are sool variables that refer to it. Once the object is unreachable from sool, the sool runtime should dispose of the object and reclaim the memory for later use.

This forms one part of memory safety: a reference is never becomes invalid, since the garbage collector will never destroy an object still being refered to.

The second part of memory safety is ensured by the core concept that no reference variable shall be uninitialized. The rules of the language and the compiler ensure that every usable reference has been previously set to a valid object. There is no "null" pointer in sool. Instead, the language provides optional variables, the validity of which is ensured by syntactic constructs.

Lexical conventions

sool source code is interpreted as a sequence of Unicode characters encoded in UTF-8. Although all language tokens are in fact restricted to the ASCII range, the string literals are interpreted directly as UTF-8.

sool is a free-form language: white spaces and comments are ignored, except when they separate tokens that would otherwise be combined.

White space characters are: space, horizontal tab, new line, carriage return.

Names are any strings of letters, digits and underscores that do not start with a digit. Expressed as a regular expression: [_a-zA-Z][_a-zA-Z0-9]*.

The following strings are reserved as keywords for the language, and cannot be used as names:

put the list here

The following strings are the other tokens of the language:

put the list here

String literals are delimited by matching pairs of quotes('...'), or double quotes ("..."). Within a string literal, all UTF-8 byte sequences are directly interpreted as their codepoint equivalent, except the following escape sequences: \a (bell), \b (backspace), \e (escape character), \f (form feed), \n (newline), \r (carriage return), \t (horizontal tab), \v (vertical tab), \\ (backslash), \" (double quote), \' (single quote), and the following numerical escapes which directly encode the Unicode codepoint represented by their hexadecimal sequence:

  • \x followed by two hexadecimal digits
  • \u followed by four hexadecimal digits
  • \U followed by eight hexadecimal digits

A backslash followed by any other character than the previously described escape sequences is invalid.

String literals can also be delimited by matching double brackets ([[...]]), in which case no escaping occurs within. Such string literals are called long strings and can be nested. For instance the following strings are equivalent:

[[String start [[substring]] end of string]]
"String start [[substring]] end of string"

Integral constants are strings of decimal digits ([0-9]+) or 0x followed by hexadecimal digits (0x[0-9a-fA-F]+). Numerical constants are strings of decimal digits which contain exactly one dot, in neither first or last position, and optionally followed by e and decimal digits ([0-9]+\.[0-9]+(e[0-9]+)?).

Note that a single dot is a valid token after an integral or numerical constant, even witout separation, because the grammar ensures that outside of a numerical constant, a dot is always followed by a name (which cannot start with a digit):

250.print
3.6.sin

Comments begin with a double hyphen -- anywhere except within a string. If the following text is not a long string, the comment is a short comment, and lasts until the end of the line. Otherwise, it is a long comment, which runs until the end of the long string.

Modules and packages

sool source code is organized in modules and packages.

A module is a single sool source file. The module name is taken to be the source file name, stripped of its path and .sool extension. A module is composed of first-level items: class definitions, interface definitions, extensions and foreign interface declarations, and module imports:

module := { module-import | class-def | iface-def | extend-def | foreign-def }

Two items in the same module cannot have the same name.

A package is a directory containing sool source files and possibly other packages. Likewise, the package name is the name of its associated directory. Packages are used to group related modules together, and provide namespacing to prevent conflict between modules with the same name.

Root source locations

The compiler is always invoked on a main module, and from there considers a certain number of root source locations:

  • the directory in which resides the main module
  • one or more library directories, defined by implementation and options to the compiler

Paths

The absolute path of a module is its location with respect to the root source location which contains it. It is written as the colon separated sequence of directories (ie. packages) to follow from the root source location down to the module source file:

module-path ::= { Name ':' } Name

However, in source code, paths are relative to the module in which they are used. Modules and packages are first looked for in the directory of the current module, then progressively up the hierarchy of directories until reaching a root source location, then in the library directories.

The compiler should report a conflict if a package or module is not found, if a module was expected but a package was found and vice-versa, or if several packages or modules with the same name are found in a same directory.

Note that the absolute path is a special case of relative path (since the root source locations are the last search locations of relative paths). Furthermore, a module can refer to itself with any suffix of its absolute path, assuming no name conflicts (since the search goes from the module's directory up to the root source location).

Compilation context and module imports

A module can contain any number of imports, with the following syntax:

module-import ::= 'import' module-path

A module import has two effects:

  1. bringing the imported module in the compilation context, that is the set of all modules that are compiled and linked together to form the final program. The compilation context therefore consists of the main module and all the modules recursively imported from it.
  2. creating shortcuts to access the imported module's items unqualified.

Indeed, within a module, first-level items can be used by their name alone, and any item in the compilation context can be used by prepending the path of the module it is defined in and a colon:

item-name ::= [ module-path ':' ] Name

When an item name not starting with a module path appears in the source, the item is first looked for in the current module, then in the imported modules, then in the modules that these import, and so forth. If the symbol is found in multiple modules at the same depth of importation, the ambiguity is signaled as an error by the compiler.

It is not an error to import modules which define items with the same name, only to use this name unqualified: they can still be accessed without ambiguity using the module paths. It is not an error either to have modules recursively import each other, directly or indirectly. Note also that it is valid to use any of the current module's paths to qualify its own items, albeit never necessary, considering the previous rules.

Types

sool is statically and strongly typed, meaning that the type of all variables and expressions is decided at compile time, through explicit declaration or infering. Additionally, all assignments are checked for compatibility, so that a given variable always holds values or object of a same class.

class-name ::= item-name [ template-args ] | '#' class-name
template-args ::= '|' ( class-name | '(' list-class-name ')' )

The name of a class - like any other item - can be prefixed by a module path, and can also be followed by template arguments. Template arguments are introduced by a pipe character, followed either by a single class name, or a comma separated list of class names between parentheses.

As a syntactic shortcut, the standard array class can be written with as hash sign followed directly by the template argument, without a pipe.

A type declaration is a class name followed by optionality information, represented by a question mark:

type ::= class-name [ '?' ]

Optional types

Variable of optional types can either hold an actual value (instance of a value class or reference to an object), or the special value nil.

Optionals cannot be sent messages, or assigned to non optionals. Optionals are converted to they non optional equivalents using boolean evaluation, which is ensured by syntax (see relevant section).

Classes

sool is a class-based language, meaning that all data is instanciated from classes:

class-def ::=   ( 'object' | 'value' ) Name [ template-def ]
                { member-def | method-def | ctor-def }
                'end'

A class is made of members, methods, and constructors. The members of an instance represent its data: variables that can in turn contain values or references to other objects. The methods are actions that can be performed on this data: they contain the actual code, the instructions that will be executed when the program is run. The constructors are special procedures, used to initialize objects and values at their instanciation.

Methods

method-def :=   'method' prototype
                block
                'end'
prototype :=    [ list-type ] method-name '(' [ list-arg-def ] ')'
method-name :=  Name [ '=' ] |
                binop | 
                '[' ']' [ '=' ]
arg-def :=      type [ Name ]

A method takes in any number of arguments, which appear as local variables in its block of code, and returns any number of return values.

Note that "value" in this context doesn't mean that a method can only return instances of value classes, but rather that "returning an object" is actually returning a reference to an object, which is indeed a value. The semantics of passing an argument, returning a value and assignment are equivalent, and will be clarified in the section on assignment.

The name of a method can be a simple identifier, a binary operator, or the brackets representing indexing. Indeed, binary operations and indexing in sool are simply message sending. Likewise, a method name can be followed by an equal sign, as the assignment operation is sometimes sending a message.

Arguments are normally declared with a type and a name, but only the type information is necessary. If its name is omitted, however, the argument will not be usable in the method's block.

The information of the method name and its arguments' types is called the method's selector. Indeed, when sending a message to an instance, this information is used to select which method to run. If a class implements a method with a certain selector, it is said to answer to this selector.

In light of this, no two methods in a class can have the same selector.

The information of the method's selector and return types is called its protoype. The set of method prototypes implemented by a class is called its interface.

Members

member-def ::= type Name [ '=' exp ]

Declaring a member with type T and name n does two things:

  • reserving room for a variable of type T in the memory layout of the class
  • creating the following accessors for the member:
    • a getter with prototype T n(), that returns the value of the member
    • a setter with prototype n=(T), that sets the value of the member to that of its unique argument

Accessors are methods like any other, except that their code is compiler-provided. In particular they contribute to the interface of the class, and follow the rule that no two methods can have the same selector. From this follows that no two members in a class can have the same name.

A member may have an explicit initializer introduced by an equal sign (see instantiation).

Classes cannot recursively contain members of their own class, through a chain of value class members or non-optional object members, as this would lead to infinite recursion in initialization.

Embedded members

A member can also be declared as an embedded member:

member-def ::= 'embed' class-name [ '=' exp ]

An embedded member is in every aspect similar to a regular member, except that its name is exactly its type, and that its type cannot be an optional. From the usual rule about methods, it follows that a class cannot embed another one more than once.

Additionally, the class provides automatic forwarding of messages to its embedded members. That is, if:

  • an instance of the class is sent a message
  • the class does not answer itself to the message
  • exactly one of its embedded members answers to the message

then the message is passed on to the embedded member as if it was the original recipient. If more than one embedded member answers to the message, the ambiguity results in an error.

Note that it is not an error to embed multiple classes that answer to the same message, only to actually send that message to an instance of the embedding class. The ambiguity can always be solved by explicitly using the getters of the embedded members.

By "forwarding", it is meant the the class actually implements a method with the same prototype as the embedded member's method, that simply sends the same message to the embedded member, and returns the returned values. This compiler-provided method is like any other method, and in particular it participates to the interface of the class.

Constructors

Constructors and are special methods that are involved in the process of instanciation.

ctor-def := 'new' '(' [ list-arg-def ] ')'
            block
            'end'

Constructors do not have names or return values and cannot be called explicitly like other methods. They are run only when invoked using the instanciation expression. Two constructors in the same class cannot have the same set of arguments.

When a constructor is invoked, the class is instanciated as follows:

  • for an object class, dynamic memory is allocated
  • members that have an initializer (default, or explicit) are initialized in the order they appear in the class definition
  • the constructor is run
  • for an object class, a reference to the object is returned. For a value class, the entire instance is returned.

The default initializer for a member is:

  • for a non-optional value type: the argumentless constructor for its class, if it exists
  • for an optional type: nil

Constructors and explicit member initializers follow additional constraints:

  • a member getter can only be called after the member is initialized
  • sending a message to self other than the member accessors, passing self as method argument, or returning from the constructor can only happen once all members have been initialized

Thanks to default initializers, this leaves only value members without argumentless constructors and non-optional object members to be explicitly initialized.

Implicit constructors

The compiler provides the following constructors, if they are not explicitly implemented:

  • the argumentless constructor with an empty body, if that does not result in an invalid constructor according to the previous rules
  • a trivial constructor which maps its arguments' types to the class members, in the order they are defined, and proceeds to assign each passed value to the corresponding member

Factories

The constructor syntax with the addition of return types is used to declare factories. No two factories or constructors can have the same set of arguments.

ctor-def := 'new' list-type '(' [ list-arg-def ] ')'
            block
            'end'

A factory is not exactly a method in that it is not executed by an instance. It does not have a self variable.

When a factory is invoked through the instanciation syntax, its body is executed, and the return values are returned as the result of the instantiation expression.

Note that the return type does not have to be the same as the class or even a single value. Factories are meant as an alternative way to create instances of the class, and add for example error notification or internizing mechanisms, but they can in fact be used as general purpose "functions".

Interfaces

Modules may define interfaces. An interface is simply a set of prototypes.

iface-def :=    'interface' Name [ template-def ]
                { prototype | 'embed' class-name }
                'end'

And interface can embed other interfaces, to inherit their prototypes. Two protoypes in an interface can have the same selector only if they are identical (ie. have the same return type).

Interfaces cannot recursively embed themselves.

A class that implements all prototypes of an interface is said to comply with this interface.

Generic classes

Defining an interface automatically create a generic class of the same name, that can be used wherever a regular class could be: class member types, method argument and return types, local variables, template arguments, and so forth. A generic class cannot be instanciated, but any object of a class that complies with it can be casted to the generic class and stored in a variable of the generic type.

A generic object then answers to exactly the messages defined in the interface, and runs the implementations that were defined in its original class.

Note that value classes cannot be directly casted to generics: they need to be "boxed" inside objects first. Furthermore, once casted to a generic, there is no way to cast an object back to its original class: it loses all its properties, except the ones defined by the interface.

Code involving generic classes should be implemented as dynamic dispatch: having the same machine code apply to any complying class through the use of method pointers. A compiler may offer optimization options, where code applied to a generic class - but whose actual class is known at compile time - can be specialized for higher execution speed.

Templates

Classes and interfaces can be defined as templates, if they contain template parameters:

template-def ::=    '|' '(' list-template-param ')'
template-param ::=  class-name Name

A template parameter is an interface, the bound, followed by a name. Template parameters are unspecified classes, that are only assumed to comply with the interface set as their bound. In particular, instances of the parameter classes can only answer to the messages in their bound. The unspecified classes cannot be instanciated.

The parameters are only assigned actual classes when the template is specialized, that is, used with existing class names as template arguments. The arguments are required to comply with the corresponding bounds. Once specialized, a class template is exactly equivalent to a similar class that would have been written directly with the specific classes, and the same rules apply (selector conflicts in particular).

Note that template arguments can be both object and value classes, as long as they comply with the bound. They can also be generic classes.

Class templates should be implemented as actual code duplication, as it is the expected behavior for a compiler: trade execution speed for binary size.

Extensions

Extending existing classes

Any existing class can be extended by adding new methods to it:

extend-def :=   'extend' class-name
                { method-def }
                'end'

The new methods must not conflict in selector with those in the class definition, or those defined in other extensions of the same class in the same module.

When looking up for methods, first the original class definition is searched, then the extensions in the current module, then the extensions in the imported modules, then those they import, and so forth. If two methods with the same selector are found at the same depth of importation, an error is produced.

The ambiguity can be lifted by prepending the method name with the path of the module it is defined in.

Non conflicting methods defined in extensions contribute to a class's interface like any other method.

Template extension

A class template can be extended as well:

extend-def :=   'extend' Name template-def
                { method-def }
                'end'

The template parameters bounds and names need not match the original ones, but the bounds must comply with the originals.

A template specialization is extended with the methods of all the extensions for which its arguments are compliant. If this results in selector conflicts from extensions in a same module, it is an error to specialize the template with this set of arguments.

Method lookup and contribution to class interface happen the same way as for regular class extensions.

Generic class extension

A generic class can be extended like a regular class, in which case objects casted to the generic class can use the methods directly.

Furthermore, implicit casting to a generic type happens when:

  • trying to send a message on an object that does not answer to it itself
  • a certain number of generic classes answer to this message
  • the object complies with exactly one of these generic classes, or one generic class is closer in the import depth that the others

If the object complies with more that one generic class that answers to the message and these classes are at the same import depth, the ambiguity is signaled by an error and must be lifted with explicit casting.
